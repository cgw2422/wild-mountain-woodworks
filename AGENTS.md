# Wild Mountain Woodworks — project conventions

- **Content lives in the database, not code.** Never hardcode public copy or photographs. Page structure is defined in `src/lib/cms/definitions.ts`; content is edited in admin. Every public image is a `Media` foreign key rendered with `CmsImage` (slot ratio + focal point).
- **Money is integer cents.** Prices are always recomputed server-side via `src/lib/pricing` (`loadConfigurableProduct` → `priceConfiguration`). Never accept a price from the client.
- **Quotes/orders store immutable `ConfigurationSnapshot`s** (`src/lib/pricing/snapshot.ts`). Don't read live product data to describe a historical request.
- **Archive, don't delete** records that history depends on (products with quotes/orders, add-ons, option groups attached to products).
- **Quotes, revisions, invoices, payments and orders are never deleted** — void them (`voidQuote`/`voidInvoice`, with `voidReasonText`, who and when). Database triggers refuse row deletes on these tables and on `ActivityLog`/sales `StatusEvent`s; never add a delete action or work around the triggers. Numbers are never reused. New numbers come only from `nextNumber` (`src/lib/sales/numbers.ts`: atomic per-prefix counters, WMWQ-/WMWO-/WMWI- from 2001); never compute one from a count or max, and never rewrite historical WMQ-/WMO-/WMI- numbers. Display the stored `number`, never a label rebuilt from a prefix.
- **Admin security is non-negotiable.** Auth is Better Auth (`src/lib/auth/auth.ts`) — never add home-grown session/password code. Every admin page calls `requireAdmin()`/`requireOwner()`, every admin action uses `adminAction`/`ownerAction`, every admin API route uses `guardAdminApi` (server-side, deny by default; UI hiding is never the control). Two-factor is mandatory. Log security-relevant changes with `logActivity` (never secrets). Keep `tests/integration/auth.test.ts` passing and extend it for new privileged operations.
- **Admin mutations** use `adminAction` (`src/lib/admin/action.ts`), then `logActivity(...)` and `revalidateSite()`. Admin forms use `ActionForm`; public forms use `usePublicForm` (never a bare `<form action>` — React resets it on error).
- **Public forms** validate with lightweight client rules (`src/lib/validation/shared.ts`) and authoritative Zod schemas on the server (`src/lib/validation/forms.ts`); `tests/unit/client-validation.test.ts` keeps them in sync. Keep Zod out of client bundles.
- **Sales** are resolved server-side at request time (`activeSale` in `src/lib/pricing/sale.ts`, applied in `resolveConfigurableProduct`). Sales are stored as entered (`saleType` PERCENT with `salePercentBps`, or FIXED_PRICE with `salePriceCents`); for percent sales advertise the entered percentage, never one recalculated from the rounded price. Never trust a browser price; list sale products with `activeSaleWhere()`, not hardcoded IDs.
- **Required default content** (new CMS pages/sections, settings, one-time starter records) goes in `src/lib/seed/defaults.ts`, which must stay insert-only and idempotent: it runs on every Railway deploy (`npm run deploy:prepare`). Sample/demo content belongs only in `prisma/seed.ts`.
- **Railway config:** `railway.json` (deprecated Config as Code; must move to Infrastructure as Code before Dec 1, 2026 — see `docs/railway-deployment.md`). Its pre-deploy command must stay `npm run deploy:prepare`; `tests/unit/deploy-config.test.ts` guards the contract.
- **Sales are quote → invoice → order, never cart/checkout** (`src/lib/sales/`). Never add carts or Buy Now. Each order has ONE invoice (created at acceptance, carrying the deposit); every payment — deposit, final balance, cash, check, Terminal — applies to it, and "Mark balance due" never creates a second invoice. Online payments use one-time Stripe Checkout Sessions per payment (`src/lib/sales/checkout.ts`: amount computed server-side from the invoice, `mode=payment`, never save cards); in-person cards use server-driven Stripe Terminal `card_present` PaymentIntents (`terminal.ts`), recorded PENDING until a verified webhook/status check confirms them, never marked paid by hand; not Stripe Invoicing (legacy only), never Stripe Quotes. Checks are PENDING until cleared; overpayment needs an owner override. Production stages are only `PRODUCTION_STATUSES` (`status.ts`); status changes go through `updateOrder` (logged `StatusNotification`, a failed email never rolls back the status). Sent quote revisions are immutable (edit via a new revision); only the customer's current sent revision can be accepted. Totals, deposits and payment status are recomputed server-side (`totals.ts`, `ledger.ts`); payments are never deleted (void/refund). Customer pages (`/quote|invoice|order/[token]`) get data only from `src/lib/sales/views.ts` — never internal notes, ids or costs. Stripe sits behind `salesFlags().onlinePayments` (Settings switch + `STRIPE_SECRET_KEY` + `STRIPE_WEBHOOK_SECRET`); only signature-verified, idempotent webhooks mark anything paid — never a redirect or success page. Sales actions use `permittedAction("sales"|"finance")`. **Affirm/Klarna (BNPL) only ever finance the FULL order total**: every Checkout Session has a purpose (`DEPOSIT` / `FINAL_BALANCE` exclude BNPL via `excluded_payment_method_types`; `FULL_PURCHASE_FINANCING` is the whole invoice total, only while nothing is paid or pending — `financingAmountFor` in `ledger.ts`) and records a `FULL_PURCHASE` payment that leaves nothing owed; never offer BNPL for a deposit, a partial amount, a balance or a change order, never alter a financed payment (bill changes as a separate invoice). Never set `payment_method_types` on Checkout (Stripe picks eligible methods), never state financing terms ourselves ("when eligible", "subject to approval"; `financingClaimIssue` guards it, including any mention of financing a deposit) — plan wording comes only from Stripe's messaging element for the full total.
- **The business name is written in full: "Wild Mountain Woodworks"** (copy, emails, documents, metadata, Stripe descriptions, seed content). The short form appears only inside the logo artwork; `tests/integration/numbering-brand.test.ts` scans for it.
- **Configurable add-ons** (e.g. Dining Chairs) are `AddOn`s with their own option groups (`AddOnOptionGroup` → the shared option library); never hardcode a specific add-on. Price per unit = add-on base + chosen adjustments, × quantity, recomputed server-side (`priceConfiguration`). The configured add-on travels as its own line with structured `addOn` details (`AddOnLineDetails` in `src/lib/pricing/snapshot.ts`) on quote, order and invoice lines — keep it grouped under its product, never flatten its choices into the main product's options.
- Class names go through `cn()` (tailwind-merge), so caller classes override component defaults.
- Before finishing work: `npm run check`, `npm run build`, and `npm run qa` against a running server.
